# Software Factory — Decision Log

Architectural and design decisions for the factory itself. Per-project decisions are tracked in each project's `session/decisions.md`.

## Resolved

| # | Decision | Resolution | Rationale |
|---|----------|-----------|-----------|
| 1 | Worker spawning mechanism | `claude -p` headless CLI (not Agent() tool) | Full Claude Code sessions; skills load properly via `--agent` flag; workers can nest subagents |
| 2 | Skill loading in workers | Preloaded via `--agent` flag (not embedded in prompt) | `claude -p --agent` loads agent definition + skills from `.claude/skills/`; embedding was a workaround for Agent() tool which didn't reliably load skills |
| 3 | bold-design: template vs generic skill | Generic (reads CLAUDE.md at runtime) | CLAUDE.md is single source of truth; skill never needs re-onboarding on context change |
| 4 | verify-ui: template vs generic | Template (bakes in port/slug/command) | Code examples in dev-browser scripts need concrete values |
| 5 | render.yaml generation | Programmatic in onboard.py | Conditional sections (backend? database? frontend?) need code logic, not string replacement |
| 6 | Design context | Onboarding question with auto-default from domain | Low friction (Enter for default), high value (populates CLAUDE.md's Design Context for bold-design) |
| 7 | V1 platform scope | Render only | Vercel/Fly.io adapter structure documented for future |
| 8 | Worker resource cap | `--max-budget-usd 50` per task (safety net) | High enough to never trigger on subscription plans; prevents true runaways only |
| 9 | Completed task file movement | `mv` to `session/tasks/completed/` by orchestrator | At-a-glance status; clean separation of active vs done; workers always write to `session/tasks/` |
| 10 | Worker execution order | Sequential (one at a time) | Safer for autonomous execution; avoids file conflicts; simpler debugging |
| 11 | Development workflow | Infrastructure-first; backend deploys before frontend begins | Frontend hits a real API + real DB from the start; no mocks, no local DB, no environment drift |
| 12 | Backend testing | Tests run against REAL Render PostgreSQL (via .env credentials) | No SQLite substitutes; integration tests catch what mocks miss; infra-worker creates .env in Phase 1 |
| 13 | Frontend local dev | Local dev for visual iteration; post-deploy verification on live URL | Local = fast visual changes; deployed = real integration test |
| 14 | Git push | Human pushes (intentional checkpoint) | Code review + auth; Render auto-deploys on commit; orchestrator raises blocker, human pushes |
| 15 | Human pre-flight | Human creates Render Blueprint Instance before orchestration | One-time manual step; after this, orchestrator deploys via push + auto-deploy |
| 16 | Render DB plan | Basic-256mb ($6/month) | Persistent, no 30-day expiry like free tier |
| 17 | Monorepo structure | `frontend/` and `backend/` subdirectories, same repo | Render `rootDir` scopes commands to each directory; both services auto-deploy on push |
| 18 | Authentication | Clerk (V1 default), configurable during onboarding | Don't roll your own auth; Clerk handles sign-in/up, JWT, session management |
| 19 | Auth is infrastructure | Auth middleware set up as first backend task, before user-specific endpoints | Models with user_id depend on auth; endpoints that need auth can't be tested without it |
| 20 | Worker spawning mechanism (supersedes #1, #2, #8) | Native subagents via the Task tool; skills preload from agent frontmatter | Fresh context per subtask without custom process machinery; `claude -p` spawning, `--agent` loading, and per-worker dollar caps retired — the /goal turn cap is the safety backstop |
| 21 | Operating structure | Committed `briefs/` Kanban board: 1-backlog / 2-active (WIP 1) / 3-blocked / 4-done; folder location IS status; the brief is a self-contained card (requirements, execution protocol, task breakdown, progress log, blockers) | Durable multi-brief operation across sessions; human-readable at a glance; single source of truth (supersedes session/spec.md + phases/ + tasks/ + turn-log.json) |
| 22 | Drive to completion | `/goal` prompt generated by the spec skill; condition = brief in a terminal folder, proven by `ls briefs/*/` each turn; turn cap = 3×requirements+10 | Loop enforced by harness, completion judged by an independent checker model; long-running allowed, infinite impossible |
| 23 | Blocked ≠ done | Two distinct terminals: `4-done/` (outcome: completed) vs `3-blocked/` (outcome: needs-human, announced as "NEEDS HUMAN INTERVENTION"); routing by requirement state; park-and-continue until zero runnable subtasks | Human blockers must not stop unrelated work, and must never be conflated with success |
| 24 | Enforcement via hooks | Stop hook blocks turn end if the active brief wasn't updated; PostToolUse hook writes deterministic trajectory.jsonl per subagent call | Documentation and eval trajectory are harness-guaranteed, not instruction-followed |
| 25 | Render workspace pin (closes the open "Render workspace name" item) | Onboarding question writes `.claude/render-workspace`; a fail-closed PreToolUse(Bash) hook blocks Render CLI/API commands unless `render workspace current` matches, and only permits `render workspace set` to the pinned name | Guarantees the factory can never touch another Render workspace/account, even if instructions drift |
| 26 | Render-only wizard (2026-09-16) | `onboard.py` offers only `render` / `none`; Vercel and Fly removed from the menu until an adapter exists | Choosing an unsupported platform silently installed no deploy skill, leaving the infra-worker unable to load its skills |
| 27 | Workspace pin auto-detected, name + ID | Onboarding reads `~/.render/cli.yaml` (`workspace`, `workspace_name`) and writes both lines to `.claude/render-workspace`; templates use the ID for `render workspace set` | Workspace names can carry trailing whitespace; the ID is stable. No network call needed, so it works even with an expired token |
| 28 | Explicit hook list | Hooks copied by name from `HOOK_FILES`, not by globbing `*.sh` | A glob leaked iCloud "file 2.sh" duplicates into every onboarded project |
| 29 | Full gitignore on fresh projects | The "create" branch writes the same list as the "append" branch (`session/`, `.env`, `.env.local`, `.claude/.turn-marker`, `.claude/settings.local.json`) | A brand-new project would otherwise have committed `backend/.env` (real DB credentials) at the first push checkpoint |
| 30 | Render credential resolver + long-lived key (2026-09-16) | `.claude/scripts/render-api-key.sh` resolves env → `.claude/settings.local.json` env block → `.env` → `render login` token; onboarding asks for a long-lived API key (hidden input) and writes it to `settings.local.json`; the guard hook falls back to `GET /v1/owners` with that key when the CLI cannot answer | The login token expires (observed: a month-old token returning 401); an autonomous run that outlives it blocks mid-brief. The Render CLI honors `RENDER_API_KEY`, so one exported variable serves CLI, curl, and hook |
| 31 | Deterministic preflight | `.claude/scripts/preflight.py` (stdlib) checks tools, git remote, credential + expiry, workspace pin vs owners, and `render.yaml` vs live services/databases/env group/secrets/health; `/preflight` skill explains; `/orchestrate` runs it when pulling from backlog and parks FAILs as blockers | Four manual Dashboard steps sit between onboarding and the first run; previously the first sign of a missed step was an infra-worker blocker several turns in |
| 32 | The contract (2026-09-16) | Clone → wizard → new repo with live services. Stated in CLAUDE.md as an invariant; no per-project manual prerequisite may sit between the steps | Every earlier design put a Dashboard step (Blueprint Instance) between the wizard and the first run; a non-developer stalls there |
| 33 | Provisioner replaces the Blueprint prerequisite (supersedes #15 and the "never create via API" rule) | `.claude/scripts/provision.py` applies render.yaml through the API: env groups, databases (wait for available, open external access), services from the GitHub remote, group links, cross-service URLs, supplied secrets, `backend/.env`, `.claude/render-services.json`. Idempotent by name, pinned by owner ID, never deletes. Runs at the end of onboarding and as the infra-worker's first task; preflight points at it. Blueprint Instance remains an optional alternative applier | Jobseeker already provisioned via API successfully; the rule existed only to avoid the wrong workspace, which the guard hook and explicit `ownerId` now guarantee. Removing the Dashboard step is the largest single reduction in manual work |
| 34 | Two wizard modes, one config | `--quick` (default: four questions; nextjs/fastapi/postgresql/render; no env group; push_policy factory; Quick Start section in CLAUDE.md; broad permission allowlist) and `--custom` (stack, auth, env group, push policy). `mode` and `push_policy` are ProjectConfig fields; templates branch on rendered values, never on separate files | Developers and non-developers use the same factory; two template sets would double the test surface |
| 35 | Push policy | `human` (deploy subtask raises an external-action blocker) or `factory` (the runner pushes, records the SHA, spawns verification; workers still never push). Read from CLAUDE.md by the orchestrate skill | The review checkpoint has no value for someone who cannot read a diff, and it was two interventions per brief |
| 36 | Secrets live in `.claude/settings.local.json` | Wizard writes RENDER_API_KEY and Clerk keys (hidden input) to its `env` block; Claude Code injects them into every Bash call; provision.py reads Clerk keys from there for `sync: false` vars | Gitignored, per-project, no shell-profile edits, one file to rotate |
| 37 | Live smoke test of the contract (2026-09-17) | Quick Start wizard → private GitHub repo → `provision.py` created `factory-smoke-db` (basic_256mb, ~2.5 min to available), `factory-smoke-api`, `factory-smoke-frontend` in nealdes.ai; both first deploys `live` within ~1 min of creation; `/health` and `/api/health` → 200 (frontend 502 for ~10 s of cold start, then 200); preflight live path 17 PASS; DB reachable from the laptop via `backend/.env`; `provision.py --destroy` removed all three | Confirms the three-step contract end to end with no Dashboard step. Render assigned suffix-free URLs this time (`factory-smoke-api.onrender.com`); the URL pass handles either |
| 38 | Teardown is first-class | `provision.py --destroy` deletes the declared services and databases by name after the human types the slug (`--yes` skips); env groups untouched; removes `.claude/render-services.json` | Spinning a project down should be as scripted as spinning it up; a smoke test that leaves paid resources behind is a failed smoke test |
| 39 | `/start` is the entry point; Claude Code is the only prerequisite (2026-09-18) | A skill in the factory repo drives `onboard.py` with `--yes` and answer flags, installs missing tools, and walks the human through GitHub login and the three Render account steps one at a time; `bootstrap.sh` and all Homebrew instructions removed | A non-developer has Claude Code and nothing else. Anything that requires them to install tools or read a prerequisites wall before Claude is involved defeats the purpose |
| 40 | Render CLI optional everywhere | preflight PASSes without it; deploy skill is API-first (logs via `/v1/logs`); guard hook already falls back to the API; `--check` never asks to install it | The API key is the credential and every operation has an API path; the CLI was only ever a convenience |
| 41 | Quick Start build verified end to end (2026-09-18) | Project `factory-notes` created by the non-interactive wizard (repo + provisioned Render); `/spec create` run headlessly with answers supplied; `/orchestrate` driven by a shell loop as a stand-in for `/goal`. Brief 001 (4 requirements) reached `4-done/` in ONE runner turn, ~42 min: 7 subtasks, 0 blockers, 0 retries; runner pushed twice under `push_policy: factory`; 11 backend tests against Render Postgres; corkboard frontend verified by local screenshot and live; both deploys live; health 200. Torn down with `provision.py --destroy`. Findings: (1) headless runs need the project marked trusted or hooks/settings are skipped — interactive users get the trust dialog; (2) Homebrew builds Node from source on macOS 13 (Tier 3) — `/start` now installs the official prebuilt tarball into `~/.local`; (3) the frontend-worker left test notes on the live board — acceptable for a smoke test, worth a cleanup step in real projects | Proves the whole contract plus the build phase for a Quick Start project with no human input after the interview |

## Open (V2 Candidates)

- **Replace dev-browser with Claude Code's built-in browser** — verify-ui, the frontend-worker, and settings.json all assume the third-party `dev-browser` CLI; the built-in browser (July 2026) would remove the only undocumented install step
- **Refresh skeleton versions** — the Next.js skeleton pins `next ^14` / `react ^18`; verify a newer pair builds on Render before bumping
- **Vercel deploy adapter** — Needs SKILL.md.tpl with Vercel CLI commands and API reference, plus a wizard choice
- **Fly.io deploy adapter** — Needs SKILL.md.tpl with flyctl commands, plus a wizard choice
- **Parallel worker execution** — Currently sequential; could speed up independent tasks within a phase
- **Authentication provider templates** — Clerk, Auth0, NextAuth patterns as optional skills
- **Worker budget per type** — Frontend workers may need higher budgets than backend (more iterations for visual work)
- **`--resume` for interrupted workers** — Currently always fresh spawn; resume could save cost for long tasks
- **Multi-service render.yaml** — Current generation is basic; could detect monorepo structure and generate more sophisticated blueprints
